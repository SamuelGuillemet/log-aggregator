# Local Cluster Log Aggregator

## Overview

A local-first web application for aggregating, parsing, correlating, and visualizing logs generated by multiple instances of a clustered application.

The application runs entirely on the developer's machine and monitors one or more log directories in real time.

---

# Goals

- Monitor multiple log directories simultaneously.
- React instantly to file changes.
- Merge logs into a unified timeline.
- Correlate events across cluster instances.
- Provide a responsive web interface.
- Remain lightweight with minimal dependencies.
- Require no external services or databases.
- Be extensible through parsers and plugins.

# Functional Requirements

## Log Sources

The backend shall support multiple log sources.

Sources are defined as a flat list loaded from a configuration file. The UI shall expose a single source selector instead of separate environment, country, and Tomcat selectors.

Each source contains:

- Unique identifier
- Name
- Dropdown group
- One or more complete log directories

Example:

```json
{
  "id": "worker-01",
  "name": "Production - Worker",
  "group": "Production",
  "directories": ["C:/Logs/Worker1", "//worker-02/logs"]
}
```

The backend shall use each directory exactly as configured and shall not append an environment-specific or Tomcat-specific path. Relative directories are resolved from the source configuration file's directory.

The application name input shall offer autocomplete values discovered from supported log filenames in the selected source while remaining editable for applications that have not emitted a log yet.

The backend shall watch the source configuration file and update connected clients after valid changes without requiring a restart. Invalid changes shall leave the last valid source configuration active.

---

## File Watching

The backend shall detect:

- new files
- deleted files
- renamed files
- modified files

Watching should use native OS events.

Polling should be avoided whenever possible.

---

## Tail Reading

The application shall:

- remember the last read position
- read only appended content
- support log rotation
- recover after application restart

The file selection rules shall include the following naming formats:

- ACCOUNTING-API-serveur.YYYY-MM-DD-N.log
- ACCOUNTING-API-fwk.YYYY-MM-DD-N.log

Where:

- YYYY-MM-DD is the log date
- N is a numeric index starting at 0

---

## Parsing

Each line should be transformed into a normalized event.

Example

```json
{
  "timestamp": "...",
  "instance": "worker-02",
  "level": "INFO",
  "thread": "Main",
  "message": "Player connected",
  "requestId": "ABC123"
}
```

Parsers should be pluggable.

---

# Event Bus

Every parsed event is published internally.

Consumers include:

- WebSocket broadcaster
- Statistics engine
- Correlation engine
- Search index
- Recording service

No module should directly communicate with another.

---

# Correlation Engine

The engine shall merge events using configurable keys.

Possible keys:

- Request ID
- Session ID
- Player ID
- Transaction ID
- Thread ID

Result:

```
15:01 API
15:02 Worker
15:03 Database
15:04 Export
```

instead of separate log streams.

# Non-Functional Requirements

## Startup

Application startup should complete in under five seconds.

---

## Memory

Avoid loading complete log files into memory.

Only maintain a configurable rolling buffer.

---

## Fault Tolerance

Parser failures must not stop processing.

Malformed lines should generate warning events.

---

## Extensibility

New parsers should require no modification of existing code.

Use interfaces for:

- parser
- event consumers
- log source providers

# Success Criteria

The application is considered successful when it can:

- Watch multiple cluster log directories simultaneously.
- Display new log entries in real time.
- Merge all events into a single chronological timeline.
- Correlate related events across different instances.
- Maintain a responsive UI under heavy log throughput.
- Be extensible with new parsers and analysis modules.
